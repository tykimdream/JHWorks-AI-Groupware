# 제한된 결재 목록의 다음 계약 — M5-02 설계 검토

구현 전 검토 문서다. 현재 API 응답이나 화면은 이 문서로 바뀌지 않는다. [실측 baseline](approval-list-baseline.md)에서1000건의 assigned JSON은2201274bytes였다.

## 함께 바꿔야 하는 소비자

1. `approvals/page.tsx`: 본문 미리보기, 휴가 일수, 전체 이력 수, 제목·상태·금액·작성자·수정일을 표시한다. 전체 본문·details·line 배열 대신 명시적 preview/leaveDays/lineCount가 필요하다. scope·검색·페이지를 URL에 보존하고 상세 왕복 시 같은 페이지와 행 포커스를 복원해야 한다.
2. `work-home.tsx`: 전체 mine/assigned를 받아 DRAFT/PENDING/REJECTED 수와 다음 문서를 클라이언트에서 계산한다. 목록만 제한하면 카운트가 틀려지므로 서버의 상태별 전체 집계와 최근4건/우선 문서를 따로 제공해야 한다.
3. `enterprise_tools.py`: 전체 내 문서를 가져온 뒤 Python에서 status 필터·limit를 적용한다. 필터·limit를 DB로 옮기고 전체 total과 반환된 일부 items를 구분해야 한다.
4. API 문서·유형·회귀·성능 도구도 같은 계약을 따라야 한다. 기존 API에서 상세 응답을 기대하는 테스트를 새 의미에 맞게 대조하고 무작정 삭제하지 않는다.

## 다음 PR을 위한 결정 기준

- 요약 응답은 화면이 필요한 고정 길이 정보만 담는다. 본문·첨부 메타·회차별 코멘트 전체는 상세 API에서만 읽도록 검토한다.
- 기본 페이지20/상한50을 시작안으로 검토한다. status/type/검색을 서버에서 적용하고 전체 일치 개수와 현재 반환 개수를 구분한다.
- 정렬은 `updated_at DESC, id DESC`를 사용한다. 동률은 결정적으로 정렬하되 페이지 사이 수정으로 문서 위치가 이동할 수 있음을 계약에 적는다. 정렬 안정성과 snapshot 일관성은 다르다.
- offset은 URL 페이지 복원과 총 페이지 안내가 간단하지만 큰 offset 비용과 수정 중 중복/누락 가능성이 있다. cursor도 수정 가능한 updated_at을 쓰면 snapshot 문제를 자동 해결하지 않는다.1000건의 query plan/HTTP/UI 결과와 탐색 요구를 보고 확정한다.
- 새 요약 endpoint를 추가할지 기존 응답을 버전 전환할지 정하고, 기존 공개 클라이언트와 함께 배포할 수 있는지 확인한다. 새 endpoint만 추가하고 기존 무제한 경로가 사라졌다고 주장하지 않는다.
- 모든 조회·집계·Tool은 기존 actor/workspace visibility를 재사용해야 한다. count/상태 집계도 권한을 적용하기 전에 계산하지 않는다.
- 보완 대상 조회나 중복 후보의 기존 상한·권한은 이 목록 변경과 섞지 않는다.

## 검증 조건

권한별 전체 수와 반환 행, 같은 updated_at의 페이지 경계, status/type/검색 조합, 빈 마지막 페이지, 수정 중 페이지 이동의 정의, home 전체 카운트, Tool 부분 결과, 상세에서 원래 목록 행 복귀를 검증한다. 같은 합성 자료로 payload·SQL·서비스 시간과 HTTP/UI 결과를 다시 기록한다. 인덱스는 실제 계획을 본 뒤 결정한다.

## 1차 요약 API

`GET /api/v1/approvals/summaries`는 기존 목록과 같은 사용자·공간 권한을 적용하고 `scope`, 선택적 `status`, `limit`(기본 20, 최대 50), `offset`(0~10000)을 받는다. `total`은 필터에 일치하는 전체 건수이며 `items`는 해당 페이지만 반환한다. 제목·본문 미리보기(최대 200자)·작성자·상태·금액·휴가 일수·결재선 수·수정 시각만 제공하며 첨부·이력은 상세에서 조회한다. 수정 시각과 ID 내림차순으로 정렬한다. 페이지 이동 사이에 문서가 수정되면 중복 또는 누락될 수 있다.

이 API는 기존 전체 목록을 대체하지 않고, 현재 홈·목록 화면은 여전히 기존 API를 사용한다. 서버 페이지는 관계 데이터를 최대 50개 문서로 제한하지만 각 문서의 결재선은 읽는다. 목록 소비자와 홈 전체 집계 전환, query plan 및 동일 fixture HTTP/브라우저 전후 측정은 후속 작업이다. PostgreSQL 검증은 전용 CI에서 수행한다.
