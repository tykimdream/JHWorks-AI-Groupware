### A1: 바로 다음 실행 단위

기존 [정리 리허설 계획](demo-retention-rehearsal.md)을 이어간다. 새 정리 시스템을 만들 필요가 없다.

1. 읽기 전용 SQL로 현재 head·공간·만료 epoch·피드백 보존·관계·backup 신선도를 확인한다.
2. 자연 만료 후24시간 대상이 있으면 대상 ID와 전후 보존 항목을 고정한다. 없으면 기다리거나 기존 계획의 별도 시간 조정 실험을 구체화한다.
3. 기존 전용 Job·이미지·신원·Secret version과 batch1 실행 산출물을 준비한다. 실제 적용 전 대상과 삭제 범위를 확인한다.
4. dry-run→대상 일치 확인→apply→재실행0을 검증하고 기존 자료 보존을 비교한다. 실패하면 자동 반복하지 않는다.

### A3: 운영 설정에서 먼저 결정할 것

- 정리 주기는 우선 시간당1회·batch5를 검토한다. 이는 제안값이며 비용·IAM·중첩 실행·실제 배포값을 확인한 뒤 확정한다.
- 하루20회 생성, 보관30공간, 세션 만료 후24시간 보존의 조합을 시간축으로 검증한다. UTC 날짜 경계에서 유입이 몰리면
  정상 정리 중에도 보관 상한에 도달할 수 있다. 단순 상한 증가 대신 예상 거부율과 안내·회복 시점을 먼저 정한다.
- 보관 상한 때문에 거절된 신규 시도도 일일 생성 예산을 소비하는 현재 계약을 확인한다. 포화 상태의 반복 클릭이
  예산을 소진하는 시나리오와 다음 UTC 날짜까지의 회복 안내를 테스트하고, 정책 변경 필요성을 판단한다.
- workspace와 feedback 정리는 각각 commit하므로 부분 성공을 기록한다. 실패 단계·삭제 건수·최근 전체 성공을 함께 본다.
- 실패 알림과 누락 알림을 따로 검증한다. 시간당 실행을 채택하면 최근 성공3시간 초과를 초기 누락 기준으로 검토한다.
- 백업은 첫 공개 때 검증된 수동 절차와 목표/한계를 명시하고, 예약 백업·보존·복구 목표는 자동 배포 전에 완성한다.

### A4~A6: 공개 경험에서 빠뜨리기 쉬운 것

- 기존 public-demo E2E는 생성·제출·승인의 일부를 `page.request`로 실행한다. API 검증은 유지하고 실제 폼/버튼 조작 경로를 추가한다.
- 현재 Hosting의 `default-src 'none'`은 정적 준비 화면용이다. 그대로 앱에 적용하면 스크립트 등 동적 자산을 막는다.
  준비 화면 검증기의 rewrite 금지 계약도 유지하고 앱 공개용 설정/검증을 별도 설계한다.
- 공간 요청100회는 일반적인 시간당 요청 제한과 다르다. 인증 전 경로·정적 자산·readiness 등 적용 범위를 목록화해
  소규모 합성 요청으로 거부/회복을 확인한다. 공개 서비스에서 부하 실험하지 않는다.
- 공개 모드는 AI off를 강제한다. 화면에 이용 불가와 수동 업무 경로를 안내하고, 포트폴리오에는 기존 검증 범위를 명시한
  AI 시연 영상·화면·평가 기록을 함께 둔다. AI 메뉴 클릭이 곧 유료 provider 호출로 이어지게 하지 않는다.
- public IAM 범위와 Cloud Run 직접 URL 접근 시 경계를 확인한다. 공개 변경 대상에 private staging을 포함하지 않는다.

## 진행 관리와 문서 정리

한 번에 실제 적용하는 작업은 하나로 제한한다. 각 작업은 다음 항목을 남긴다.

- 문제/사용자 영향, 범위, 선행 조건, 완료 조건.
- 코드·설정·데이터 변경과 검증 환경, source SHA와 실제 배포 digest/revision.
- 검증 결과·실패 기록·남은 한계·복귀 절차.
- 다음 작업과 외부 적용에 필요한 확인 사항.

roadmap은 큰 마일스톤, current-status 상단은 현재 상태와 다음 작업, 개별 실행 문서는 증거를 담당한다.
