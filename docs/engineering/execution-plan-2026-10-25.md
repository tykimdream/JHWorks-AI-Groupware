첫 단위는 **M0-01의 경비 과제 기준을 고정하면서 M2-01의 기존 평가 사례를 대조·확장하는 PR**이다.

## 2. M0 — 제품·사용성 기준

### M0-01 대표 업무 계약 — verified (문서·기존 구현 대조)

- 문제/대상: 필요한 양식을 모르는 작성자, 사실·규정을 확인하는 결재자.
- 산출물: 경비 제품 명세와 작성→질문→근거→저장→보완→제출→결정의 상태별 성공/실패 조건.
- 정상 과제: 고정 기준일·가상 조직·정책 버전을 가진 CES 17만원 합성 사례. 상대 날짜는 고정 기준일로 해석한다.
- 실패 과제: 지출일/사용처 누락, 모순된 후속 답변, 미래 지출일, 정책 근거 부재, 모델 장애,
  반려 후 수정, 오래된 문서 버전, 만료·예산 소진을 구분한다.
- 완료: 각 화면의 다음 행동·서버 검증·AI가 모르는 사실·명시적 확인 지점을 기존 API/화면에 연결한다.
- 검증: 실제 구현과 대조해 이미 있는 기능과 새로 고칠 부분을 표시한다. 본문/필수값을 모델이 임의 보완하지 않는다.

### M0-02 신규 사용자 과제 실험 — waiting_external (절차·빈 양식 준비)

- 기존 [휴가 비교 절차](../portfolio/task-study.md)는 보존하고 경비 전용 절차·기록 양식을 만든다.
- 초기 제안은 신규 사용자 3~5명. 미확보는 waiting_external이며 개발자 자체 실험을 신규 사용자 결과로 바꾸지 않는다.
- 같은 합성 과제·시작/종료 화면·데이터 snapshot·viewport·제품 revision을 사용한다.
- 올바른 완료, 소요 시간, 수동 수정 필드, 막힌 단계, 도움 요청, 실패와 중단을 기록한다.
- 공개 수동 경로와 실제 AI 경로의 비교는 두 조건이 준비된 뒤 동일 조건에서 한다. fake AI 결과는 별도다.
- 익명 참가 식별자와 과제 결과만 보관한다. 실제 영수증·개인/회사 정보·원문 대화·세션/키를 분석 도구에 전송하지 않는다.
- 완료: 원시 기록과 작은 표본의 한계, 반복된 장애 목록을 남긴다. 실패를 분모에서 빼지 않는다.
- 외부 참여자 연락/모집은 사용자가 정한 범위에서 진행한다. 대기 중 M1/M2 offline 작업은 계속한다.

## 3. M1 — 최소 지속 운영

### M1-01 기존 증거·현재 상태 대조 — planned

- 시작점: [기존 정리 운영](demo-retention-operations.md), [실행 대조](demo-retention-rehearsal.md),
  기존 정리·방문자 수명·보존 경계 코드/회귀. 미커밋 운영 문서는 보존하고 배포된 사실로 간주하지 않는다.
- 대조 대상: 현재 job/scheduler 상태, dry-run 여부, workspace 누적/만료, 보존·삭제 경계,
  실행 신원·고정 이미지·백업/복원 참조·기존 실패/누락 알림 증거.
- 완료: 이미 확인한 항목과 추가로 필요한 항목만 표로 정리한다. 실제 새 백업이 없으면 신선한 백업으로 표시하지 않는다.
- 범위 제한: 새 모니터링 플랫폼·반복 장시간 관찰은 포함하지 않는다. 이미 받은 알림·실행을 불필요하게 재현하지 않는다.

### M1-02 남은 정리 적용과 회복 검증 — planned

- 의존성: M1-01의 실제 부족 항목, 실제 삭제/예약 적용 범위와 보존·복구 조건 확인.
- 기존 dry-run·첫 대상/건수·실행 상한·보존 대조 gate를 재사용한다. 무제한 일괄 삭제를 추가하지 않는다.
- 완료: 승인 범위의 정리 후 보존 대상 유지, 재실행의 중복 삭제 없음, 다음 체험 가능성을 확인한다.
  예약을 켠 경우 정상 예약 실행 기록을 별도 확보한다. 아직 실행되지 않은 예약은 verified로 표시하지 않는다.
- 실패: 중단/비활성화·수동 회복 절차와 책임을 기록한다. 실패 감지와 장시간 성공 누락 실험의 상태를 구분한다.
- 외부 조건 대기는 M2의 평가·예산 코드 구현을 막지 않는다. 제품 작업의 선행 운영 과제로 확대하지 않는다.

## 4. M2 — 경비 AI 평가·비용 제한·공개

### M2-01 사례 목록화와 offline 평가 — verified (데이터·채점 계약, 실제 모델 미실행)

- 시작점: 기존 `apps/api/evals`, `app/evals`, `expense_model_smoke` 및 초안 provider/서비스 회귀.
- 기존 사례를 먼저 분류하고 의미가 겹치는 테스트를 복제하지 않는다. 초기 회귀셋은 기존 것을 포함해 30~50개를 목표로 조정한다.
- 범주: EXPENSE/TRAVEL 구분, 단위·금액·날짜, 모르는 값 null, 후속 질문, 모순·수정,
  규정 근거 부재/버전, 허용되지 않은 요청, 모델 시간 초과/잘못된 구조, 사용자 확인 전 무변경.
- 각 사례에 고정 입력·기대 구조/질문·허용 근거·필수 여부·오류 분류를 정의한다.
- 완료: fake/계약 검사와 실제 모델의 평가 결과를 구분하는 재현 명령·report가 있고, 필수 사례 실패가 승격을 차단한다.
- 이 단위는 유료 모델을 호출하지 않는다. 기존 실제 2건 결과는 재사용하지만 새 평가 전체의 정확도로 환산하지 않는다.

### M2-02 capability와 서버 비용 예산 — planned

- 의존성: M0-01의 경비 계약. M2-01과 일부 독립 준비 가능.
- 처음 공개할 유료 기능은 경비 초안·후속 질문으로 한정한다. 기존 전역 AI 설정을 켜 다른 검토/Tool/Agent까지 노출하지 않는다.
- 서버 capability allowlist와 클라이언트의 사용 가능 표시를 함께 설계한다. UI 숨김을 접근 제한으로 사용하지 않는다.
- 방문자별/전체 기간별 호출·토큰/비용 예산, 입력 크기, 최대 출력, timeout, 동시 호출과 재시도 상한을 명시한다.
- 다중 요청이 예산을 동시에 통과하지 않도록 기존 PostgreSQL 원자적 admission 패턴을 검토·재사용한다.
  호출 전 보수적 예약, 실제 사용량 정산, 실패/재시도·정산 누락의 처리 정책을 계약으로 남긴다.
- GCP spend cap과 AI provider 예산은 별개다. 실제 가격·모델·환율/과금 단위는 유료 실행 준비 시 확인한다.
- 장애·예산 소진·비활성화는 명확히 안내하고 직접 작성과 기존 입력을 보존한다.
  예시 재생을 제공하면 실제 AI 응답과 구분한다.
- 완료: 동시 admission·한도·실패·재시도·계정/방문자 경계 회귀 및 공개 OFF의 기존 업무 흐름이 통과한다.

### M2-03 실제 평가와 제한 공개 — planned

- 의존성: M2-01/02, 원격 운영 대조, 적용할 키·모델·서버/provider 예산·호출 횟수·공개 capability 범위.
- 유료 호출은 일반 CI와 분리한다. 이미 승인된 범위를 먼저 대조하고 부족한 외부 적용 승인만 구체적인 안으로 확인한다.
- 고정 회귀 사례로 시도/성공·실패 종류·필드 정확성·근거·지연·토큰/비용을 보고한다. 전체 평가 여부와 표본을 명시한다.
- 필수 사례에서 사실 조작·잘못된 권한/근거·확인 없는 쓰기가 발견되면 공개 승격을 중단한다.
- 고정 source/digest 후보에서 정상·장애·소진 대체 경로를 확인한 뒤 실제 도메인의
  요청→질문→초안 확인·저장→수동 제출→역할 전환·승인을 검증한다.
- 완료: 실제 모델 결과와 공개 경로, 사용 예산, 되돌릴 feature flag가 기록된다. 로컬 결과만으로 공개 완료를 주장하지 않는다.

## 5. M3 — UX·프론트엔드

### M3-01 공통 서버 데이터 수명 — planned

- `useCurrentEmployee`, `useDemoConfiguration`, 화면별 조회를 조사해 중복 요청·소유권·갱신 경계를 정한다.
- 기존 context/전용 store와 query cache 도구를 비교하고 규모에 맞는 한 가지 방식으로 설명한다. 라이브러리 설치 자체를 완료 기준으로 삼지 않는다.
- 계정/방문 공간/역할 변경·로그아웃 시 이전 캐시를 노출하지 않는다. 요청 취소·오래된 응답 무시·mutation 후 무효화를 유지한다.
- 완료: 같은 데이터의 중복 요청 감소를 고정 화면에서 비교하고 계정 전환·지연 응답 역전·재시도 회귀를 통과한다.

### M3-02 입력·탐색 맥락과 상태 표현 — planned

- scope/목록 위치→상세→복귀, 작성 중 취소/이동, 만료/네트워크 실패의 입력 보존을 계약으로 정한다.
- 저장 중·성공·빈 결과·실패·오래된 버전의 문구와 재시도 경로를 일관되게 만든다.
- 로컬 임시 보존을 쓰면 보존 범위·만료·계정 분리·로그아웃 정리를 정의한다. 민감한 입력을 장기 보관하지 않는다.
- 완료: 사람 실험에서 관찰한 장애 또는 재현 가능한 문제를 수정하고 동일 과제로 재검증한다.
  아직 사용자 결과가 없으면 구현 가설로 표시한다.

### M3-03 경비 보완·검토의 다음 행동 — planned

- 기존 누락/중복 제안에 원문 비교·보완 위치·다시 확인 행동을 연결한다.
- 반려 사유→수정 항목과 결재자용 핵심 사실·근거 요약을 후보로 검증한다. 실제 모델을 쓰는 부분은 M2 예산을 따른다.
- 중복 가능성을 확정 판정으로 바꾸거나 제안만으로 제출/반려하지 않는다. 근거 문서의 열람 권한을 보존한다.
- 완료: 사용자가 이유와 해결 행동을 찾을 수 있는지 과제 검증, 원문·버전 대조, 읽기 전용 경계 회귀.

### M3-04 낙관적 UI — deferred (제품 필요 확인 후)

- 실제 필요한 가역 동작(예: 제안 숨기기/다시 보기)이 생길 때 적용한다. 기술 시연을 위한 별도 기능을 억지로 추가하지 않는다.
- 처리 중 표시·실패 시 복구·중복/순서 역전·권한 변경을 검증한다.
- 승인·금액·연차 확정은 서버 성공 후 표시한다. 기존 낙관적 동시성 제어를 UI 구현으로 소개하지 않는다.

## 6. M4 — 디자인 시스템·Storybook·패키지

### M4-01 실제 폼·상태 컴포넌트 — planned

- 기존 토큰/Button/Badge를 재사용하고 Field·Input·Select·Alert·EmptyState·Dialog를 실제 중복과 사용 맥락에서 추출한다.
- 기본·오류·disabled·pending·긴 문구·키보드/포커스·상태 알림·reduced motion 계약을 정의한다.
- 실제 제품의 대표 경비 흐름과 Pattern 문서가 같은 컴포넌트를 소비해야 한다.
- Tailwind는 영역별로 적용하고 이전한 CSS를 제거한다. 토큰 값을 중복 선언하거나 무조건 모든 CSS를 없애지 않는다.
- 완료: 적어도 대표 폼/확인 흐름에서 소비되고, 필수 정보가 툴팁 안에만 숨지 않으며 관련 UI 회귀가 통과한다.

### M4-02 Storybook과 정적 배포 — planned

- M4-01의 컴포넌트 상태를 stories로 재현하고 필요한 interaction/키보드·접근성 검사를 연결한다.
- props·합성 데이터만 사용한다. 실제 회사/사용자 자료·키·인증 세션·운영 API에 의존하지 않는다.
- Pattern 문서는 원칙·업무 사용법, Storybook은 상태·동작 재현으로 역할을 나눈다. 토큰/예제를 따로 복제하지 않는다.
- 정적 빌드·상대 경로·asset·CSP/iframe 동작·공개 범위를 확인하고 기존 호스팅 또는 정적 호스팅을 선택한다.
  새 비용/게시 권한이 필요한 경우 그 적용 범위를 준비한다.
- 완료: 정적 결과물과 CI 검증, 실제 배포 URL에서 대표 stories·직접 링크·키보드 동작 확인.

### M4-03 npm 공개 — deferred (게시 조건 확정 후)

- 이름/소유권·라이선스·version/변경 기록·공개 API·peer dependency·CSS/Tailwind 소비 경계를 확정한다.
- tarball 내용·exports/types·Next 외 소비 앱·기본 button type/ref/aria·반응형/접근성을 검증한다.
- 기존 private 패키지를 준비 완료 전에 public으로 바꾸지 않는다. 게시 credential은 저장소에 넣지 않는다.
- 완료: 게시를 결정한 경우 승인 범위의 registry에서 설치·실행을 확인한다. pack 성공은 npm 공개 완료가 아니다.

## 7. M5 — 목록·DB·성능

### M5-01 동일 조건 baseline — planned

- 로컬 격리 PostgreSQL과 fake AI에서 합성 문서/결재 회차 분포를 고정한다. 작은 규모→1천/1만 등으로 자원을 확인하며 늘린다.
- 목록/상세·역할별 query count/time/plan, 응답 크기, API 지연/오류, 브라우저 DOM/렌더링을 측정한다.
- warm/cold·동시성·환경·반복 횟수·revision을 기록한다. 공개 데모에 부하를 주지 않는다.

### M5-02 제한된 목록 계약 — planned

- M5-01의 baseline 후 목록 요약 DTO·페이지 크기 상한·검색/필터/정렬·안정적인 tie-breaker를 설계한다.
- offset/cursor를 비교하고 데이터 변경 중 중복·누락 계약을 정의한다. 목록에서 본문/details/이력 전체를 매번 전달하지 않도록 검토한다.
- FE의 URL/탐색 맥락과 업무 조회 Tool을 함께 갱신한다. 서버 제한 후 한 페이지만 보고 전체 결과라고 표현하지 않는다.
- 완료: author/assigned/workspace 권한, 동률 정렬·페이지 경계·업데이트·total 의미와 기존 클라이언트 호환 검증.

### M5-03 재측정·동시성 — planned

- 같은 baseline으로 DB/전송/API/렌더링을 재측정하고 인덱스는 실행 계획으로 검증한다.
- 기존 version/lock/unique 기반의 별도 연결 경합·응답 유실·재시도·rollback 회귀를 재사용한다.
- 완료: 원시 결과와 전후 비교·부작용·한계를 보관한다. 개선이 없으면 그 결과도 기록한다.
- 캐시/가상화/추가 병렬 처리와 더 큰 데이터 실험은 측정된 병목과 자원 여유가 있을 때만 추가한다.

## 8. M6 — 배포·관측·복구

### M6-01 공개 release workflow 통합 — planned

- 임시 태그·이전 revision·DB migration 호환성·백업 참조·비밀값 비노출을 검증한다.
- 완료: 정상 배포와 실패 복구를 격리된 환경에서 재현하고 공개 도메인의 배포 source를 확인한다.

### M6-02 최소 관측·백업/복원 — planned

- 기존 JSON log/request ID·알림을 재사용하고 외부 health/readiness, 오류·지연·실제 체험 시작 실패·한도·비용을 구분한다.
- 상시 합성 체험을 생성해 일20회/보관30공간을 소모하지 않는다. 읽기 점검과 실제 요청 지표를 우선한다.
- 화면 오류→요청 ID→원인·복구로 연결되는지 확인하고 개인정보/원문 프롬프트의 수집을 피한다.
- 백업 주기·보존·실패·복원 목표를 제안하고, 실제 clean restore와 데이터 대조 시간을 기록한다.
- 완료: 필요한 감지·복구가 한 번 재현되고 보관/비용/한계가 문서화된다. 이전 백업 증거와 새 실행을 구분한다.

## 10. 재개·검증·승인 경계

- 다음 실행은 `git status` → roadmap → 본 문서 → 해당 ID의 기존 구현/증거 순으로 읽는다.
  기존 미커밋 `demo_retention_operations.py`와 정리 문서 초안을 덮어쓰거나 이 계획 PR에 섞지 않는다.
- 이미 승인된 일반 구현·PR·리뷰·병합은 다시 묻지 않고 진행한다. 실제 삭제·새/확장 권한·유료 호출·키 업로드·새 공개 범위는
  기존 승인을 대조한 뒤 부족한 구체적 적용만 확인한다. 계획 문서는 그 실행을 대신 승인하지 않는다.
- 코드별 필요한 검사 후 저장소 CI를 통과하고 리뷰 범위를 기록한다. 실제 배포는 source/digest·검사·결과·복구 경로를 남긴다.
- 외부 조건 때문에 막히면 `waiting_external`과 필요한 입력을 적고 가능한 로컬/독립 작업을 수행한다.
- 작업 종료 기록: `ID / 소스·PR / 상태 / 실제 검증 / 외부 적용 / 남은 조건 / 다음 ID`.
- 제품 AI가 아직 공개되지 않았다면 공개 OFF로 유지해 표현한다. 승인 없는 유료 실험·서비스 활성화·npm 게시를 수행하지 않는다.
